  <name>Task 2: Create and apply database schema migration</name>
  <files>

  <action>
    1. Create `supabase/migrations/001_foundation.sql` containing the FULL database schema from RESEARCH.md Pattern 7, with these critical elements:

       **Enums:**
       - `professional_role`: agent, lender, inspector, title_company, appraiser, contractor
       - `application_status`: draft, submitted, approved, rejected, waitlisted
       - `zip_tier`: premium, standard, suburban

       **Tables:**
       - `applications` — all fields from RESEARCH.md (id uuid PK, created_at, updated_at, step_completed, status, Step 1 fields, Step 2 fields, Step 3/payment fields, legal fields, admin fields, tracking fields including session_id)
       - `application_zips` — junction table (id uuid PK, application_id FK, zip_code, is_primary, created_at, UNIQUE(application_id, zip_code))
       - `zip_seats` — one row per ZIP per role (id uuid PK, zip_code, role, total_cap, phantom_count, tier, neighborhood, created_at, updated_at, UNIQUE(zip_code, role))
       - `email_log` — audit trail (id uuid PK, application_id FK, email_type text, sent_at, provider_message_id, status)
       - `out_of_area_interest` — demand signal capture for non-Houston ZIPs (id uuid PK, zip_code text NOT NULL, role professional_role, created_at timestamptz DEFAULT now(), ip_address text, user_agent text). This table captures interest from the seat checker when a non-Houston ZIP is entered, per CONTEXT.md decision: "Non-Houston ZIPs: accept any US ZIP in the seat checker but show 'Coming soon to your area' — captures demand signal from outside Houston."

       **Critical index:**
       ```sql
       CREATE UNIQUE INDEX applications_email_role_active_unique
         ON applications (email, role)
         WHERE status != 'rejected';
       ```

       **RLS policies (use `(select auth.jwt())` for performance — cached per statement):**
       - Enable RLS on ALL five tables (applications, application_zips, zip_seats, email_log, out_of_area_interest)
       - `zip_seats`: public read for anon + authenticated (landing page seat checker)
       - `zip_seats`: admin write (approver only for mutations, viewer + approver for select)
       - `applications`: anon INSERT with check (true) — applicants are not auth users
       - `applications`: anon SELECT where session_id matches (for form recovery)
       - `applications`: admin SELECT for authenticated with approver/viewer role
       - `applications`: approver UPDATE for authenticated with approver role
       - `application_zips`: anon INSERT with check (true) — created with application
       - `application_zips`: admin SELECT for authenticated
       - `email_log`: admin SELECT for authenticated
       - `email_log`: no public access
       - `out_of_area_interest`: anon INSERT with check (true) — public seat checker writes demand signals
       - `out_of_area_interest`: admin SELECT for authenticated — admin views demand data

       **Updated_at trigger:** Create a `set_updated_at()` trigger function and apply to `applications` and `zip_seats`.

    2. Apply the migration using the Supabase MCP `apply_migration` tool with name `foundation_schema` and the full SQL content.

    3. Update `prisma/schema.prisma` to mirror the database schema:
       - Set datasource to `postgresql` with `DATABASE_URL` env var and `DIRECT_URL` for direct connection
       - Define all models matching the SQL tables: `Application`, `ApplicationZip`, `ZipSeat`, `EmailLog`, `OutOfAreaInterest`
       - Use appropriate Prisma field types matching the Postgres types
       - Map enum types to Prisma enums
       - Define all relations (Application hasMany ApplicationZip, Application hasMany EmailLog, etc.)
       - Use `@@map("applications")`, `@@map("application_zips")`, etc. to match SQL table names
       - Use `@map("column_name")` for snake_case column names

    4. Run `npx prisma generate` to generate the Prisma client with types.
